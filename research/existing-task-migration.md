# What happens to an existing task when the script drops its model config items and requires SDK 1.14.0?

Research for [#122](https://github.com/cerealdevnull/Script-AI-Browser-Agent/issues/122).

Sources (read-only):

- Desktop client `Cereal-Automation/desktop-client`, `origin/master` at `abc7256`. That commit is the merge of [PR #114](https://github.com/Cereal-Automation/desktop-client/pull/114) "LlmComponent for scripts with an app-wide API key" (spec #103), merged 2026-10-16. "Old client" means the parent `abc7256^1`, which builds against SDK 1.13.0. "New client" means `abc7256`, which builds against 1.14.0.
- SDK `Cereal-Automation/sdk`, tag `1.14.0` (`4893cb0`).
- This script, `origin/master` at `50d4c7f`.

Paths below are relative to `cereal-client/src/main/java/com/cereal/client/` in the desktop client unless they say otherwise.

## Setup facts

- The client's SDK version is `BuildConfig.SDK_VERSION`, generated from `libs.versions.cereal.sdk` (`cereal-client/cereal-client.gradle.kts:63-67`, `infrastructure/data/repository/ApplicationRepositoryImpl.kt:15`). It is `1.13.0` before PR #114 (`gradle/libs.versions.toml:43` at `abc7256^1`) and `1.14.0` after (`gradle/libs.versions.toml:44` at `abc7256`).
- This script's `manifest.json` has `"sdk_version": "@cereal-sdk-version@"`, which `build.gradle.kts:96-100` fills from `gradle/libs.versions.toml:7` (now `1.13.0`). Bumping the SDK dependency to 1.14.0 therefore sets `sdk_version` to 1.14.0 automatically.
- One rule decides "needs a newer client": `isClientUpdateRequired`, which compares **major.minor only**. A missing `sdk_version` never blocks (`domain/model/script/ScriptPackageExtensions.kt:16-25`). Install/update and the UI badges share this rule. It has been in the client since the first commit (`7734b99`), and PR #114 didn't change it (`git diff abc7256^1 abc7256` is empty for the gate files).
- A script update is only attempted when the release's `versionCode` differs from the installed one (`application/script/ScriptSyncManager.kt:157-172`). The manifest says `"version_code": 1`, so a release that drops the items must also bump `version_code`.
- The SDK says scripts that call `llm()` must set `sdk_version` to 1.14.0 or higher (`cereal-sdk/.../component/ComponentProvider.kt:41-48` at `1.14.0`). The 1.13 client's `ComponentProviderImpl` has no `llm()`, so the gate is the only thing that keeps a 1.14 script off an old client.

## 1. Values already saved in an existing task, including the stored `apiKey` secret

**They are kept in the database and ignored at runtime.** No error is raised, nothing is deleted, and the user isn't prompted.

- **Storage.** A task's configuration is one row per key in `script_configuration_item` (`key`, `EncryptedString value`, `ValueType type`). The table cascades from `script_configuration` (`infrastructure/data/datasource/database/room/entity/ScriptEntity.kt:197-225`). `SECRET` differs from `STRING` only in its type label; every value is encrypted the same way (`ScriptEntity.kt:22-26`).
- **Loading against the new definition.** `ScriptPackageInstanceMapper` loads every stored row and passes the *current* script's definition (`infrastructure/data/datasource/database/room/mapper/ScriptPackageInstanceMapper.kt:55-60`). `KeyValueRoomMapper.mapConfigurationItemsFromEntities` maps every row by its *stored* type. It never filters by key (`mapper/KeyValueRoomMapper.kt:104-117`). After the update:
  - `apiKey` (stored `SECRET`) loads as a `Secret` and stays in the in-memory values map (`KeyValueRoomMapper.kt:232-234`).
  - `model` and `baseUrl` (stored `STRING`) load as strings. `coercedToSecretIfDeclared` leaves them alone because no current item declares them (`KeyValueRoomMapper.kt:79-87, 228-230`).
  - `provider` (stored `ENUM`) resolves through the current definition's enum type. With no item for the key, it resolves to `null` and is dropped from the map, but its row stays (`KeyValueRoomMapper.kt:248-251`).
- **Validation ignores extra keys.** `ScriptConfigurationDefinition.validate` loops over the definition's `configurationItems` only. A key the script no longer declares is never looked at (`presentation/tasks/script/overview/configuration/ScriptConfigurationDefinitionExtensions.kt:22-51`). `ScriptConfigurationValuesValidator` uses it at start (`application/interactor/script/validator/ScriptConfigurationValuesValidator.kt:13-23`). [PR #60](https://github.com/Cereal-Automation/desktop-client/pull/60) is a precedent for this tolerance: it stopped a stale saved custom-dataset value from crashing validation after an update (`ScriptConfigurationDefinitionExtensions.kt:53-57`).
- **Runtime.** The script receives its configuration as a `java.lang.reflect.Proxy` over its interface. `ConfigInvocationHandler` answers only methods the interface declares (`application/task/ConfigInvocationHandler.kt:61-80`, `application/task/TaskExecutor.kt:178-194`). Once the methods are removed, nothing can read the stale values.
- **What happens on update.** `ScriptManager.updateScript` downloads the new JAR and then calls `reloadScriptInstance` for every existing instance of the package (`application/script/ScriptManager.kt:26-39`). That stops the instance's tasks and restores them from the database with the new definition (`application/script/ScriptInstanceManager.kt:30-36`). After that, the existing task runs the new script with its old `goal`/`startUrl`/etc. values, and the four stale rows are carried along unused.
- **How long the secret lives.** The client has no edit-in-place path for an instance's configuration. The only writer is `addScriptPackageInstance` (`domain/repository/ScriptInstanceRepository.kt:28`). Nothing prunes undeclared keys: the only `DELETE FROM script_configuration_item` is a one-off migration for `STRING_LIST` (`infrastructure/data/datasource/database/room/DatabaseConnector.kt:252`). So the encrypted `apiKey` row stays until the user deletes that task (the instance), which cascades. "Duplicate task" copies only keys the current form declares, so the new task doesn't inherit the stale keys (`presentation/.../model/ConfigurationItemsFormSection.kt:91-94`, `ConfigurationItemsForm.kt:56-67`). Finished-task snapshots also store key/value/type rows (`task_configuration`, `ScriptEntity.kt:290-321`, written in `mapper/ScriptInstanceMapper.kt:288`). Snapshots taken before the update may hold the old key too, until those tasks are removed.
- **Side note.** The old secret is never shown or re-used. The user has to enter a key again in Settings → AI, which is a separate app-wide store (`infrastructure/data/repository/LlmProviderConfigRepositoryImpl.kt`). Nothing migrates the per-task key there.

## 2. A user on a client older than the one with `LlmComponent`

**At update, the update is rejected and the old script version stays.** The user isn't told unless they install from the marketplace.

- Both automatic sync and marketplace install/update download the JAR and then run `readJar(..., enforceAgainstSdkVersion = installedSdkVersion)`. It throws `ClientUpdateRequiredException` when `isClientUpdateRequired(manifest.sdkVersion, …)` (`infrastructure/provider/ScriptInstallProviderImpl.kt:23-60`, `infrastructure/data/datasource/filesystem/FileSystemScriptsDataSource.kt:155-162`). The new file is deleted (`FileSystemScriptsDataSource.kt:116-119`). `updateScript` stores and validates the new JAR *before* removing the old one, so a failed SDK check "must leave the installed version in place" (`FileSystemScriptsDataSource.kt:49-67`). `reloadScriptInstance` never runs because `scriptInstallProvider.updateScript` threw first (`ScriptManager.kt:30-31`).
- In sync, per-script exceptions are caught and collected (`ScriptSyncManager.kt:102-118`). The login sync ignores the collected failures (`application/auth/UserAuthManager.kt:102-117`). So on an old client the update fails silently on every sync, and the user keeps the current release with the per-task provider, API key and model fields. Existing tasks keep working as they do today.
- Installing from the marketplace detail page shows the update-required message: `ScriptDetailViewModel` maps `ClientUpdateRequiredException` to `InstallState.Error(UPDATE_REQUIRED_MESSAGE)` (`presentation/marketplace/ScriptDetailViewModel.kt:134-136`). The exception text is "This script requires a newer version of Cereal. Please update your Cereal client." (`application/exception/ClientUpdateRequiredException.kt`).
- **At task start**, `StartScriptInteractor` refuses with the same exception whenever the installed package needs a newer client (`application/interactor/script/StartScriptInteractor.kt:35-39`). If a 1.14 JAR ends up installed on a 1.13 client anyway (for example after a client downgrade), startup loading keeps it on purpose. "My scripts" and script selection then badge it as update-required (`FileSystemScriptsDataSource.kt:215-228`, `presentation/myscripts/MyScriptsViewModel.kt:73-80`, `presentation/tasks/script/overview/ScriptSelectionViewModel.kt:101,149`), and new runs are blocked.
- **Gap (edge case only):** the per-task `TaskManager.startTask` and `restoreTasks` don't re-check the gate (`application/task/TaskManager.kt:68-91,124-126`). An already-created instance whose JAR was swapped to an incompatible one outside the update path could still run a task and fail at its first `llm()` call. The normal update path can't produce this state, because the update is rejected first.

## 3. A user on a new client who hasn't configured Settings → AI

**Nothing warns them up front. The task starts and fails at the first `llm()` call** with "No AI provider is set up. Choose one in Settings → AI."

- No start-time check: `StartScriptInteractor.run` checks the SDK gate, config validity, license, capacity and concurrency, and nothing about AI settings (`StartScriptInteractor.kt:34-85`). The manifest has no "uses LLM" flag that the client reads (`infrastructure/data/datasource/filesystem/reader/models/ManifestJson.kt`). The only reference to Settings → AI outside the settings screen is in the call path.
- At the call: `LlmComponentImpl.complete` calls `CompleteLlmRequestInteractor.run`. That reads the config fresh on every call and throws `LlmCallException.NotConfigured` before any network traffic when no provider is set up (`application/interactor/llm/CompleteLlmRequestInteractor.kt:11-26`). The bridge maps it to SDK `LlmException.NotConfigured(message)` (`infrastructure/sdkcomponent/LlmComponentImpl.kt:113-117`). The message is "No AI provider is set up. Choose one in Settings → AI." (`domain/model/exception/LlmCallException.kt:17`, matching the SDK default in `cereal-sdk/.../component/llm/LlmException.kt:15-18` at `1.14.0`).
- If the script doesn't catch it: `TaskExecutor` treats `LlmException` as an expected script error. It logs "Error executing task: …" to the task log and sets `TaskStatus.Error` with the exception's message. It doesn't report to Sentry (`application/task/TaskExecutor.kt:112-118, 215-216`). The SDK documents the same rule: "An uncaught `LlmException` fails the task with its message" (`LlmException.kt:5-8`).
- Because the config is read per call, a user who fixes Settings → AI and restarts the task gets going without editing the task. A running task picks up a saved change on its next call (`CompleteLlmRequestInteractor.kt:12-13`).
- Everything the script does before its first `llm()` call still happens. For this script that includes opening Chrome and navigating to `startUrl`, unless the script checks first. The SDK suggests that `NotConfigured` is the place for a script to "fall back to non-LLM behaviour here at no cost" (`LlmException.kt:15`). A cheap pre-flight is possible: one tiny `llm()` call before the browser starts, or catching `NotConfigured` on the first step.
- The model and API key now come only from Settings → AI. A missing model surfaces as `InvalidRequest`, plus a task-log warning naming the model set in Settings → AI (`LlmComponentImpl.kt:45-47`). A rejected key surfaces as `Authentication` ("Check it in Settings → AI", `LlmCallException.kt:20-23`).

## Implications for the migration

- Dropping the four items is safe for existing tasks on a new client. The tasks keep running, and the user only has to fill in Settings → AI once.
- The old per-task `apiKey` stays encrypted in the client DB until the task is deleted. If that matters, the release notes could tell users to delete and re-create (or duplicate) their tasks after setting up Settings → AI.
- Old-client users keep the previous script release without being told. Release notes or the store listing should say Cereal must be updated first.
- Bump `version_code` along with the SDK.
- Consider handling `LlmException.NotConfigured` before the browser opens, so an unconfigured user gets the message straight away and doesn't watch Chrome open first.
